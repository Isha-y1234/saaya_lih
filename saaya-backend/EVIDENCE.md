# Emergency evidence: CameraX and private Backblaze B2

## Delivered behavior

Home's active SOS offers **Capture emergency evidence**. Evidence is also reachable from Live Safety, Incident Chat and recipient SOS alerts. Home exposes the latest ended incident's evidence. The capture screen opens without requesting permissions or starting a recording. **Enable photo camera** requests CAMERA only; **Enable video camera and audio** requests CAMERA and RECORD_AUDIO. A further explicit capture/record tap starts capture. Video is SD, includes audio, and stops at 30 seconds or 45 MiB. The visible recording message and Stop recording button remain on screen. Backgrounding, navigation and lifecycle disposal stop recording and release CameraX. Photo and video use cases bind separately for hardware compatibility. LiveKit leaves before navigating to evidence, releasing its camera; it does not record this evidence or upload through LiveKit.

Captures stay under `Context.noBackupFilesDir/evidence/<authenticated-user>/<incident>/`, never the public gallery, external storage, backup, or Android BuildConfig. JPEG/MP4 files use UUID names and an atomic `.server` sidecar to recover the server evidence ID. A `.capture` file is renamed only on successful capture finalization (including usable duration/size/source-inactive finalization). Partial interrupted captures remain visible and preserved; they are not submitted as completed media. The app stops allowing additional capture once local evidence reaches 200 MiB (one in-flight capture may take it above that threshold). No automatic eviction of failed or partial evidence.

Upload is a separate explicit tap. Progress reports transferred bytes, with a clear notice that confirmation is still pending. A successful B2 PUT is insufficient: only a matching successful completion response with an upload timestamp permits local capture/sidecar deletion. A lost completion response is resolved by confirming the same evidence ID before any new PUT. A lost authorization response is recovered using the same UUID request ID. Files survive HTTP errors, expired URLs, disconnects and app restarts. A successful confirmation followed by a failed list refresh still reports successful confirmation accurately. There is no background capture, automatic upload, automatic resend loop or silent server deletion.

Downloads require a tap on a particular saved photo/video. Listing does not download media or poll for it. The app gets a new short-lived URL, downloads once to private cache, and grants an installed viewer read access to that specific cached file through a non-exported FileProvider. Signed URLs are never passed to an external browser. Repeating the tap intentionally downloads again. A viewer app may retain its own copy; an already downloaded copy cannot be remotely revoked. Camera/audio permission is not needed for viewing.

## APIs and authorization

All four routes use the existing bearer session dependency and the same current Trusted Circle `authorized_incident` helper as Chat/Live Safety. The owner or a recipient account with a current notification-code link to an existing contact owned by that incident owner can read. Removing the contact or link prevents subsequent list/download authorizations. FCM payloads, saved SOS phone numbers, phone matching and client-selected recipient/owner IDs grant no access.

| Method and path | Behavior |
| --- | --- |
| `POST /incidents/{id}/evidence/uploads` | Owner of ACTIVE incident only. Body: `requestId` (UUID), `mediaType` (`image/jpeg` or `video/mp4`), `fileSize` (positive integer bytes), optional `capturedAt` (timezone-aware ISO timestamp). Extra fields rejected. Returns `evidenceId`, `complete`, short-lived `uploadUrl`, `expiresIn`, required `headers`. A completed retry returns `complete: true` and public metadata without a new PUT URL. |
| `POST /incidents/{id}/evidence/{evidence_id}/complete` | Owner only. No client-selected object key or version. HEAD checks actual size, Content-Type, evidence-id metadata and a non-null B2 VersionId; a version-specific 32-byte ranged GET checks JPEG magic or MP4 `ftyp`. Only then does an ACTIVE incident acceptance write precede final metadata persistence. Returns public metadata. Already completed records are idempotently returned even after the incident ends. |
| `GET /incidents/{id}/evidence?before=<evidence-id>` | Owner/current authorized recipient. Only completed evidence, newest first, at most 50 per page, with `nextBefore` and `canUpload`. Ended incidents remain readable. |
| `POST /incidents/{id}/evidence/{evidence_id}/download` | Owner/current authorized recipient. Returns `downloadUrl`, `expiresIn` for the stored immutable B2 VersionId. Works for ended incidents. No arbitrary object key input. |

Every success response has `Cache-Control: no-store`. New upload/confirmation attempts after the incident end transition return 409, except idempotent confirmation of already completed evidence. As with Incident Chat, a conditional ACTIVE incident update is the acceptance point ordered against incident ending; an operation accepted before ending can finish its metadata write while the end request completes. A recipient may never upload or complete (403); other accounts get 404, missing/expired sessions 401; unsupported MIME/fields 422; oversized files 413; missing/mismatched object 409; expired abandoned attempt 410; storage/database failure 503.

Mongo collection `evidence` stores server-generated `_id`, `incidentId`, authenticated `ownerId`, generated `objectKey`, `mediaType`, `fileSize`, `capturedAt`, `createdAt`, `retryUntil`, state, final `uploadedAt` from B2 LastModified, and final `versionId`. Original filenames are deliberately not accepted or stored. Public metadata maps `_id` to `id` and excludes object key/version/request internals. Keys have exactly `evidence/<owner ObjectId>/<incident ObjectId>/<evidence ObjectId>`; all three identifiers are validated/resolved server-side. The unique `(incidentId, requestId)` index prevents duplicate records under concurrent retries. The `(incidentId, state, _id descending)` index supports bounded listing. Capture timestamps are normalized to UTC milliseconds for Mongo retry equality and remain client-reported, not forensic proof of time.

PUT URLs sign the exact content length, MIME type and `x-amz-meta-evidence-id`. Android sends these headers and its exact RequestBody length using a separate OkHttp client without the Saaya session interceptor, redirects, cookies or logging. URLs are bearer capabilities until expiry. Current authorization is checked when issuing each URL; an issued URL cannot be individually revoked during its short lifetime. A valid PUT URL can create another B2 version until it expires; completed evidence pins one verified version so replay cannot replace the saved evidence. Replays and unconfirmed uploads can still consume storage. Server verification reads at most 32 bytes and does not download video in full.

Pending attempts may renew URLs with the same UUID and exact media/size/timestamp for 24 hours while the SOS is active. A new UUID represents a distinct capture. Pending attempts older than 24 hours return 410 and cannot be renewed/completed; no TTL automatically erases evidence or metadata. Failed/unconfirmed objects are never listed or downloadable through these routes. An operator should review PENDING records older than `retryUntil`, correlate all B2 versions for their exact keys, and reconcile with the owner before any separately authorized cleanup. Do not apply bucket-wide expiration or automatic old-version deletion: it could destroy pinned completed versions. No deletion endpoint/job is included.

## Backend variables (Render only)

| Exact variable | Meaning / default |
| --- | --- |
| `B2_ENDPOINT_URL` | Bucket's regional S3 API endpoint, e.g. `https://s3.us-west-004.backblazeb2.com`. No bucket name/path/trailing slash. Must be HTTPS and match `B2_REGION`. Other hosts fail closed. |
| `B2_REGION` | Exact region from that endpoint, e.g. `us-west-004`; do not use an AWS region. |
| `B2_BUCKET` | Must be `saaya-evidence`, the **private** evidence bucket. Defaults to `saaya-evidence` when unset, empty or whitespace-only. An explicitly different name fails closed with 503 on storage operations. |
| `B2_APPLICATION_KEY_ID` | Standard B2 application key's `keyID` (boto3 AWS access key ID). |
| `B2_APPLICATION_KEY` | That key's secret `applicationKey` (boto3 AWS secret access key). |
| `EVIDENCE_PHOTO_MAX_BYTES` | Optional JPEG maximum, default `10485760` (10 MiB); clamped to 1024–20971520. |
| `EVIDENCE_VIDEO_MAX_BYTES` | Optional MP4 maximum, default `52428800` (50 MiB); clamped to 1024–104857600. |
| `EVIDENCE_URL_TTL_SECONDS` | Optional PUT/GET lifetime, default `120`; clamped to 30–300 seconds. |

Malformed numeric values fail startup; missing/invalid B2 configuration makes storage operations return a safe 503 without affecting SOS, calls, auth, FCM, Chat or LiveKit. Do not configure AWS shared credentials or Android B2 variables. Application secrets are supplied explicitly to boto3 in the backend and are never returned; standard SigV4 URLs necessarily contain the public signing-key identifier and a temporary signature, not the application-key secret. Keep URLs private as well. Do not enable HTTP/botocore wire debugging, request-body logging or signed-URL logging in Render, clients, analytics or proxies.

## Exact B2 bucket and application-key configuration

No bucket, account, application key or paid service has been provisioned by this code change.

1. In Backblaze B2 **Buckets**, use the bucket named exactly `saaya-evidence`; if it does not yet exist in your account, create it with that name. Set **Files in Bucket: Private** (`allPrivate`), never Public. Set `B2_BUCKET=saaya-evidence` in Render. Do not add a name suffix or silently select another bucket. If that globally unique name belongs to another account, resolve access to the intended bucket before deployment. Record the bucket's displayed S3 Endpoint and region for the variables above; the example US region is not a requirement to move your data there.
2. Set the bucket's default server-side encryption to **SSE-B2** (Backblaze-managed keys). Keep all file versions. Do not add lifecycle hide/delete rules, public/CDN distribution, public ACLs or an anonymous bucket policy. No Object Lock or paid add-on is required. B2 retains object versions by default; version-specific GETs must remain available.
3. In **App Keys → Add a New Application Key**, name it `saaya-render-evidence`, restrict **Allow access to bucket(s)** to this bucket, **Type of Access: Read and Write**, and **File name prefix: `evidence/`**. Leave **Allow list all bucket names** off; this app never lists buckets. Use a standard key, not the master key. For a key provisioned with explicit capabilities, only `readFiles` and `writeFiles` are needed by this code; it never lists or deletes objects/buckets. Console Read and Write may grant additional capabilities, so use explicit capabilities if your provisioning workflow supports them.
4. Transfer `keyID` and the once-shown `applicationKey` directly into Render's private environment editor. Do not paste either into chat, Android, `local.properties`, GitHub, a ticket, command history or this document. Keep key rotation in your password manager. Rotate by updating both Render values and redeploying, then revoke the old key after outstanding short-lived URLs expire.
5. Leave CORS unconfigured for this native Android client. Do not add wildcard origins or expose public files to make uploads work. Android supplies exact signed Content-Type, content length and evidence-id metadata; no Saaya Authorization header goes to B2.
6. Verify anonymously fetching any uploaded key fails. Verify a freshly authorized GET works, a version-specific GET works, and an expired URL fails. Confirm your bucket remains Private after deployment. These are real B2 acceptance checks, not claims inferred from configuration.

Backblaze's official [boto3 guide](https://www.backblaze.com/docs/cloud-storage-use-the-aws-sdk-for-python-with-backblaze-b2) describes custom S3 endpoints and key mapping; its [application-key documentation](https://www.backblaze.com/docs/cloud-storage-application-keys) describes bucket/prefix restrictions. This backend uses boto3, S3 Signature V4 and the S3-compatible API exclusively for evidence.

## Free-first limits

As checked on 2026-11-04, Backblaze advertises the first **10 GB of storage free**, monthly free egress up to **3× average monthly stored data**, then **$0.01/GB** additional egress. Those are account allowances, not an unlimited free evidence archive. Current pricing also says Class A/B/C transactions are free for pay-as-you-go accounts; Class D has a separate allowance/rate. See the current official [B2 pricing page](https://www.backblaze.com/cloud-storage/pricing) before relying on the allowance. No second storage provider, CDN or paid LiveKit recording/egress service is introduced.

Set B2 account usage alerts/caps in its console according to your budget. Versions, replayed PUTs and abandoned uploads count toward storage. Keep videos short; the UI downloads only explicitly selected evidence and does not autoplay, preload thumbnails, poll video bodies or repeatedly fetch on reconnect. Each completion checks only a tiny byte range. No automatic deletion is used to force the account back under quota; monitor and review retention explicitly with users.

## Two-phone manual acceptance procedure

Use two physical phones, A and B, with the debug APK and different Google accounts. Use a non-emergency test SOS phone number belonging to you; do not test by calling emergency services. Configure the private B2 bucket/Render values above before upload tests.

1. On B, open notification settings and copy its recipient code. On A add B as a Trusted Circle contact and link that code. Keep A's saved SOS call number separate. On A start SOS; confirm incident creation and the existing ACTION_CALL/dialler flow. Return to the app. On B confirm the existing FCM alert and open its incident. Record the incident ID for later checks.
2. On A Home tap **Capture emergency evidence** (or **Emergency evidence** from Live Safety/Chat). Confirm no permission dialog or recording appears merely by opening it. Tap **Enable photo camera**. On a fresh install confirm only camera permission is requested. Deny: verify the denial message and that the rest of SOS remains usable. Deny permanently: verify **App permissions** opens system settings. Allow camera there, return and tap Enable photo camera again. Keep microphone denied.
3. Tap **Capture photo**, verify visible capture status and a local Photo row. Confirm no saved/server row yet. Tap **Upload / Retry confirmation**. Verify transfer progress, waiting-for-confirmation text, then **Uploaded. Backend confirmed evidence is saved.** The local row should disappear only after that confirmation. On B tap **Emergency evidence → Refresh evidence**: see the same Photo row. B must have no capture controls. Tap **Download and open selected photo**: verify the correct image opens without camera/mic permissions. Merely refreshing must not download anything.
4. On A tap **Enable video camera and audio** and confirm microphone is requested now. Deny it and verify photos remain possible by returning to photo mode. Allow microphone, select video mode, then tap **Record short video with audio**. Verify visible RECORDING status, working **Stop recording**, and audible speech in the uploaded/downloaded clip. Repeat without stopping and verify automatic finalization around 30 seconds. Upload once; on B explicitly select the video to download/open. Refresh repeatedly and confirm no automatic video playback/download.
5. Capture another photo/video on A. Turn off A's network before Upload. Verify no success claim and the local row remains. Force-stop/reopen Saaya, return to the same active incident's evidence, restore network and retry: exactly one saved row for that capture. Repeat by dropping network during a video PUT. Repeat by restoring network after more than 120 seconds: retry must obtain renewed authorization for the same request, not duplicate metadata. If the server accepted a PUT/completion but its response was lost, Retry confirmation must recover it before uploading again.
6. During recording press Home, lock the screen or navigate Back using the system gesture. Verify camera/microphone indicators stop promptly and recording does not continue in the background. Return: finalized local media should remain available for explicit upload; a genuinely failed partial capture should be marked Interrupted capture and not offered for upload. Rotate once during capture; confirm no secret restart. Test camera-disabled system privacy settings/another camera app: show an unavailable message, allow retry and preserve saved files.
7. On A unlink B's recipient code or delete B's Trusted Circle contact. On B Refresh evidence should deny/clear the server list; opening a fresh download must fail. A previously issued URL may work until its short expiry and an already downloaded file cannot be revoked. Relink B and refresh to restore current authorization. Sign B out and into an unlinked third account on the same phone: no old account's evidence list/local captures or new download authorization may be available.
8. While another capture is still local/pending on A, end SOS through the existing End SOS control. Open evidence from Home's **View latest incident evidence** and from B's original alert/Chat. Existing saved photos/videos must list/download on both accounts while the link exists. Pending new uploads/completions must be rejected, preserving A's local file. Capture controls must disappear after refresh. An already completed upload's Retry confirmation remains safe after ending.
9. Start a new SOS on A. Its evidence list/local pending files must be separate from the original incident. Verify incident chat still works in the new SOS; old Chat remains read-only. Join/leave Live Safety, open evidence from it, then return and explicitly Join/Retry live sharing; verify there is no camera conflict. Recheck FCM, existing circle contacts, the separate saved SOS number and cellular call fallback.
10. With an authenticated developer HTTP client (keep bearer tokens and signed URLs private, out of shell history/logs), use the API table to attempt `text/html`, zero-size files, JPEG size `10485761`, and MP4 size `52428801` with default limits: expect 422/413. Attempt authorization as B: 403. Attempt A's evidence ID under a different owned incident: 404. PUT bytes/metadata inconsistent with the authorization: B2 must reject changed signed headers or completion must return 409 with no saved row. Verify two completions and two authorization retries with the same UUID produce one record. Verify a new upload to the ended incident returns 409, and an unlinked account gets 404 on list/download.
11. Using an upload grant held longer than `expiresIn` before starting PUT, verify B2 rejects it; the app's normal Retry obtains a new grant. Verify an expired GET fails and tapping Download again obtains a fresh one. Inspect the B2 console: bucket is Private, object keys are server-generated under `evidence/`, MIME/size match, versions are retained, and no public URL opens. Check Render logs for absence of credentials, signed URLs and evidence contents.
